# ADR 0011 — Code sandbox, grading and the question bank

- **Status:** Accepted (Phase 6)
- **Date:** 2026-10-05

## Context
Users solve coding problems in six languages, graded against hidden tests. User code is
hostile by default: it must never run in the API process or on the host. The brief names
Judge0. Admins manage questions, languages and limits, and can generate questions with AI,
but an AI-written question is only useful if its tests are correct.

## Decision

**A sandbox service behind one interface (`CodeRunner`).** Implementations:

- **Piston** (local default). It is free and self-hosted. It runs each program in an
  `isolate` box with no network and CPU, memory, time and output limits, and it works on
  cgroup v2 hosts such as Docker Desktop. It sits in Compose under the `sandbox` profile
  (privileged, bound to localhost); runtimes are installed once with
  `app.scripts.install_sandbox_runtimes`.
- **Judge0 CE**, the brief's choice, implemented and selectable with `CODE_RUNNER=judge0`.
  Judge0 1.13 needs cgroup v1, which Docker Desktop doesn't provide, so it suits Linux hosts
  configured for it, or a managed Judge0. Network is disabled per submission.
- **Fake**, for tests. It never executes anything; it uses scripted behaviours instead.

The API only ever sends source text to the sandbox over HTTP.

**Problems are stdin/stdout programs.** The same tests work in every language and every
sandbox, with no per-language harness to maintain. Output comparison ignores trailing
whitespace on each line and trailing blank lines.

**Grading.**
- The first test runs alone, so a compile error costs one run. The rest run in parallel,
  capped by `CODE_RUNNER_CONCURRENCY`.
- The verdict is the first failing test's.
- Hidden tests report only pass/fail and timing, never input, expected output or the
  program's output, so they can't be extracted.
- "Run" uses the visible examples and is synchronous; nothing is stored.
- "Submit" is graded in the background, and is idempotent with an `Idempotency-Key`.
- Both are rate-limited: Run in-process, Submit from the database. Phase 9 moves rate
  limiting to Redis.

**Question bank with validation.**
- An admin-created question can be published only after **every reference solution passes
  every test** in the sandbox, with at least one visible and one hidden test.
- Editing a published question returns it to draft until it is validated again, so users
  never see an unvalidated version.
- Languages (enabled, time and memory limits) are edited in the admin.
- Per-question stats (attempts, acceptance rate, solvers, average time) show which questions
  are too easy or too hard.

**AI generation with automatic validation.** The model writes the problem, test inputs and a
Python reference solution, but **no expected outputs**. The sandbox runs the reference on
every input to produce them. If the reference crashes, times out or prints nothing on any
input, the item is marked failed. Otherwise it waits for review, and an admin approves (as
draft, or published) or rejects it. This removes the most common failure of AI-written
problems: tests whose "expected" answers are wrong.

**Seed set.** Eight classic problems (two of each difficulty, plus extras) ship with Python
references. Their expected outputs were produced by running the references offline
(`app/scripts/build_seed_problems.py`), including the larger tests near the constraints.

## Consequences
- Real execution needs the sandbox running (`docker compose --profile sandbox up -d piston`).
  Without it, Run and Submit return a clear "sandbox unavailable" verdict, never a wrong
  one, and nothing executes in the API.
- Only Python references are generated by AI. References in other languages are optional
  and are validated the same way when an admin adds them.
- The code editor is a plain textarea (with Tab indentation and per-language drafts); a
  richer editor is Phase 10 polish.
